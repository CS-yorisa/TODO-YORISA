다음 단계에 따라 git commit을 수행하세요:

## 1. 상태 파악

1. `git status`와 `git diff --staged`를 실행하여 스테이징된 변경사항을 파악하세요.
2. `git branch --show-current`로 현재 브랜치를 확인하세요.

## 2. main 최신화 및 브랜치 생성

현재 브랜치가 `main`이라면 커밋하기 전에 반드시 아래 순서를 따르세요. `main`에 직접 커밋하지 마세요.

1. `git fetch origin main`으로 원격 main의 변경사항을 가져오세요.
2. `git rev-list --count HEAD..origin/main`으로 원격 main에 새 커밋(머지된 PR)이 있는지 확인하세요.
3. 새 커밋이 있다면 브랜치를 만들기 전에 **먼저 main을 최신화하고 충돌을 해결**하세요:
   - 워킹 트리에 변경사항이 있으면 `git stash push -u`로 임시 보관
   - `git merge origin/main`으로 main 최신화
   - `git stash pop` 후 충돌이 발생하면 충돌을 해결 (충돌 마커를 확인하고 양쪽 변경 의도를 모두 반영)
4. 최신화가 끝나면 `git switch -c <브랜치명>`으로 새 브랜치를 생성·이동하세요. 브랜치명은 워킹 트리의 **모든 변경사항을 대표**하도록 지으세요 (예: `feat/todo-filter`). 브랜치 이동은 `checkout`이 아닌 `switch`를 사용하세요.

## 3. 스테이징 및 커밋 분할

1. 스테이징된 파일이 없다면 `git diff`로 변경사항을 확인하고 관련 파일을 `git add`로 스테이징하세요.
2. 변경사항이 많거나 성격이 다른 변경이 섞여 있으면 **논리적 단위로 나누어 여러 번 커밋**하세요:
   - prefix가 달라지는 변경(예: 기능 + 문서, 기능 + 설정)은 별도 커밋으로 분리
   - 같은 prefix라도 서로 독립적인 작업이면 분리 (예: 모델 변경과 API 변경)
   - 각 커밋이 단독으로 이해 가능하고, 되돌리기(revert) 가능한 단위가 되도록 구성
3. 워킹 트리의 **모든 변경사항(수정·신규·삭제 파일)을 빠짐없이 커밋에 포함**하세요. 이번 작업과 직접 관련 없어 보이는 파일도 성격에 맞는 별도 커밋으로 분리해 포함합니다.
4. 모든 커밋이 끝나면 `git status`로 커밋되지 않은 변경사항이 남아 있지 않은지 확인하세요.

## 4. 커밋 메시지 작성

변경사항을 분석하여 적절한 prefix를 선택하세요:

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `style`: 포맷팅, UI/스타일 변경 (로직 변경 없음)
- `docs`: 문서 변경
- `refactor`: 동작 변경 없는 코드 구조 개선
- `test`: 테스트 추가 또는 수정
- `chore`: 빌드 프로세스, 의존성, 설정 변경

실제 변경사항을 바탕으로 커밋 메시지를 작성하고 커밋하세요:

```sh
git commit -m "prefix: 작업내용"
```

- `--no-verify`로 훅을 건너뛰지 마세요. 훅이 실패하면 문제를 해결한 후 재시도하세요.
- **커밋 메시지에 Claude 관련 내용을 포함하지 마세요.** `Co-Authored-By: Claude ...`, `Generated with Claude Code`, 세션 링크 등 AI 서명·흔적을 커밋 메시지에 넣지 않습니다.

## 5. PR 제목/내용 추천

모든 커밋이 완료되면 `.github/PULL_REQUEST_TEMPLATE.md` 형식에 맞춰 PR 제목과 내용을 추천하세요. PR을 직접 생성하지는 마세요.

- **브랜치의 모든 커밋과 변경사항이 빠짐없이 반영**되도록 작성하세요. 일부 커밋만 요약하지 마세요.
- GitHub에 **그대로 복사해 붙여넣을 수 있도록** 제목과 내용을 각각 마크다운 코드 블록으로 감싸 출력하세요. 인용문(`>`)이나 표 등으로 변형하지 마세요.
- **제목**: 커밋 전체를 대표하는 한 줄 요약 (`prefix: 작업내용` 형식)
- **내용**: 템플릿의 섹션 구조(`### 설명`, `### 관련 이슈`)를 그대로 사용
  - `### 설명` — 이 PR의 모든 변경 내용 요약 (커밋 단위 목록 포함)
  - `### 관련 이슈` — 연관 이슈 번호를 알면 `close #번호` 형식으로, 모르면 사용자에게 확인 요청

출력 예시:

````
제목:
```
feat: 할일 필터 기능 추가
```

내용:
```markdown
### 설명
- 할일 목록 상태 필터 API 추가 (`feat: ...`)
- 필터 관련 테스트 추가 (`test: ...`)

### 관련 이슈
close #12
```
````
